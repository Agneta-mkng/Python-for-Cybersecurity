# TLS (Transport Layer Security)

This is a cryptographic protocol which enables a client to communicate securely with a server over an untrusted network.

## The problem

My capture of the secure chat server showed the login as readable text: the username, the password, and every chat message.

Authentication checks **who** the client is, but it does not protect the data on the way. Anyone who can capture the traffic can read it. TLS fixes this.

## What TLS provides

| Property | Meaning |
|---|---|
| **Confidentiality** | Data is encrypted, so a capture shows unreadable bytes. |
| **Integrity** | Tampering with data in transit is detected. |
| **Server authentication** | The client can check that it is talking to the real server, using a certificate. |

TLS sits between TCP and my application. My newline-framed messages stay the same. They are encrypted before they are sent and decrypted when they arrive.

**Related terms:**

- TLS replaced SSL, which is obsolete, though Python's module is still called `ssl`.
- HTTPS is HTTP carried over TLS.

## How TLS works, built up piece by piece

### 1. Keys and symmetric encryption

Encryption has a **method** (public) and a **key** (secret). In the Caesar cipher the method is "shift the letters" and the key is the shift number. Knowing the method without the key does not help, and real keys come from such a huge range of values that guessing is impossible. The Caesar cipher has only 25 possible keys, so it is easy to break.

When both sides use the same key to lock and unlock, it is **symmetric encryption**. It is fast, so it protects the actual data.

### 2. The key distribution problem

Two strangers on the internet cannot just announce a key, because an eavesdropper hears it too. A key has to reach both sides without travelling in the open.

### 3. Key exchange (Diffie-Hellman)

Each side makes up a temporary secret that is never sent, and sends a public value computed from it. Each side then combines the other's public value with its own secret and reaches the **same** number.

```python
p = 23          # public
g = 5           # public
a = 6           # Alice's secret (never sent)
b = 15          # Bob's secret (never sent)

A = pow(g, a, p)    # Alice sends this
B = pow(g, b, p)    # Bob sends this

print(A, B)                 # 8 19
print(pow(B, a, p))         # 2
print(pow(A, b, p))         # 2
```

- Public values: `p`, `g`, `A`, `B`. Secret values: `a` and `b`.
- The eavesdropper sees all the public values but cannot get the shared number without `a` or `b`.
- With tiny numbers the secret can be found by trying every value. Real exchanges use numbers so large that this search is impossible.
- The shared number becomes the symmetric key. The key exchange does not encrypt messages itself.
- Because the temporary secrets are thrown away after the connection, stealing the server's key later does not reveal recorded traffic. This is called **forward secrecy**.

### 4. The man-in-the-middle problem

A key exchange gives me a shared secret with *someone*, but not with *whom*. An attacker in the middle could run one exchange with the client and another with the server, then read and relay everything without either side noticing.

### 5. Signatures and certificates

- A **key pair** has a private key (kept secret) and a public key (shared with anyone).
- A **signature** is made with the private key and checked with the public key.  
 Anyone can verify it, but only the key's owner can make it. If the signed data changes, verification fails.
- A **hash** is a short fingerprint of data.   
Changing any part of the data changes the fingerprint completely. The server signs a hash of the handshake.
- A **certificate** ties a public key to a name, and a certificate authority (CA) signs it.
- The certificate is public, so an attacker can copy it. But without the private key, the attacker cannot produce the signature the server makes during the handshake.

Two different checks are needed:

| Question | What proves it |
|---|---|
| Does this public key belong to the named server? | The CA's signature on the certificate |
| Does the party I'm talking to hold the matching private key? | A signature made with the private key during the handshake |

### Two kinds of private values

| | Temporary secret | Server's private key |
|---|---|---|
| Sent over the network | Never | Never |
| What travels instead | The public value computed from it | The signature made with it, plus the certificate |
| Lifetime | One connection | As long as the certificate |
| Purpose | Produce the shared secret (the encryption key) | Sign to prove the server's identity |

## The handshake (TLS 1.3)

The handshake happens after the TCP handshake and before any application data, so my login prompts travel inside the encrypted connection.

1. **ClientHello:**  
The TLS versions and cipher suites the client supports (a cipher suite is the set of algorithms to be used), a random value, the client's public key-exchange value, and the name of the server it wants.
2. **ServerHello:**   
The chosen version and cipher suite, a random value, and the server's public key-exchange value. Both sides can now compute the shared secret.  
 ***Everything after this point is encrypted.***
3. **Certificate:**   
The server's certificate.
4. **CertificateVerify:**   
A signature, made with the server's private key, over a hash of the handshake so far.
5. **Finished:**   
Both sides send a check value over the whole handshake, so any tampering would show.
6. **Application data:**   
My login prompts and chat messages, encrypted.

**What the client checks:**

- the certificate is trusted (it chains to a CA the client trusts, or to a certificate it was told to trust)
- the certificate is within its validity dates
- the name matches the host being connected to (the SAN field)
- the signature verifies against the public key in the certificate

If any check fails, the client aborts before any sensitive data is sent.

## Certificates and trust

- Normally a CA signs the certificate, and clients already trust the CA.
- For this project I will use a **self-signed certificate**, which no CA has vouched for.  
 A client will ony accept it if I tell the client to trust that specific file. That is fine for learning on my own machine, and wrong for a real service.
- **Never turn off certificate or hostname verification to make an error go away.**   
Without it, an attacker in the middle can pretend to be the server, and the encryption protects nothing against that attacker.
- **Never commit the private key.**   
The certificate (public) can be shared, but the key file stays out of the repo (add it to `.gitignore`).

## Setup: create a certificate

The certificate and key are not in the repo. Generate your own:

```bash
mkdir certs
openssl req -x509 -newkey rsa:2048 -nodes \
  -keyout certs/server.key -out certs/server.crt -days 365 \
  -subj "/CN=localhost" \
  -addext "subjectAltName=DNS:localhost,IP:127.0.0.1"
```

The client trusts `certs/server.crt`, so run the client from the same folder.
