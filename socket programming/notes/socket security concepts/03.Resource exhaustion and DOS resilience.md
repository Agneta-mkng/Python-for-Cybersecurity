# Resource exhaustion and DoS resilience

**The idea**  
A server has limited resources: memory, threads, file descriptors (every open socket uses one), and CPU time. **Resource exhaustion** means a client, by accident or on purpose, uses up one of them so the server can't serve anyone else. When legitimate users lose service as a result, it is a **denial of service (DoS)**. **Resilience** means the server enforces limits so that no single client can use more than its share.

| Resource | How it can be exhausted | Defense |
|---|---|---|
| Memory | One huge message with no newline | Maximum message length (see Check 2 in input validation file) |
| Threads and sockets | A flood of connections | Maximum number of clients |
| Threads held open | A client connects and sends nothing | Idle timeout |
| CPU and bandwidth | Thousands of valid messages per second | Rate limiting (not done yet) |

## The weak spot

My server started a new thread for every connection, with no limit on how many. A client that connected and sent nothing left its thread blocked in `recv()` forever, because no timeout was set.

**Distinction:**   
`recv(1024)` is how many bytes are read per call. The timeout is how long `recv()` waits. They are separate settings.

### Experiment: Idle connections

This script opens idle connections to my own server on `127.0.0.1` and holds them:

```python
import socket
import time

COUNT = 20
connections = []

for i in range(COUNT):
    s = socket.create_connection(("127.0.0.1", 8080))
    connections.append(s)

print(f"Opened {len(connections)} idle connections. Press Ctrl+C to close them.")

try:
    while True:
        time.sleep(1)
except KeyboardInterrupt:
    pass

for s in connections:
    s.close()
print("Closed all connections.")
```

The `COUNT` is the script's number, not the server's. The server had no limit.
`time.sleep()` keeps the script alive so the connections stay open; it does not pause the server.

**Result:**   
The server printed "Client connected" for each connection, and a normal client could still connect and get an echo.

## Defense 1: Idle timeout

```python
idle_timeout = 10   # seconds

def handle_client(client_socket, address):
    client_socket.settimeout(idle_timeout)
    ...
    except socket.timeout:
        send_error(client_socket, "Error : connection timed out")
    except OSError as e:
        print(f"Connection error with {address}: {e}")
```

- With a timeout set, `recv()` raises `socket.timeout` when no data arrives in time, instead of waiting forever.
- `socket.timeout` is a subclass of `OSError`, so `except socket.timeout` must come **before** `except OSError`, or the `OSError` handler would catch it first.
- The `finally` block closes the socket, which frees the thread.

**Why the timeout is set on each client socket, not in `server()`:**  
The listening socket's timeout would control `accept()`, not `recv()`, and accepted sockets don't inherit it. So the timeout is set on each `client_socket` after it is accepted.

**Server vs. client control:**   
The server can't stop a client from going quiet, but it decides how much quiet it will tolerate. The value is a business-rule choice (a chat app might allow minutes, a simple request-response service seconds).

**Result:**   
After the timeout passed, the idle connections were closed. 

## Defense 2: Maximum number of clients

```python
max_clients = 4
active_clients = 0
client_lock = threading.Lock()
```

In `server()`, after `accept()`:

```python
client_socket, address = m.accept()

with client_lock:
    if active_clients >= max_clients:
        accepted = False
    else:
        active_clients += 1
        accepted = True

if not accepted:
    print(f"Rejected {address}: server full")
    send_error(client_socket, "Error: server is full")
    client_socket.close()
    continue

thread = threading.Thread(target=handle_client, args=(client_socket, address), daemon=True)
thread.start()
```

In `handle_client`, the slot is given back when the client leaves:

```python
def handle_client(client_socket, address):
    global active_clients
    ...
    finally:
        client_socket.close()
        with client_lock:
            active_clients -= 1
        print("The socket is closed.")
```

**Design notes**
- **The counter has to go back down.**  
Clients leave in `handle_client`, which runs in a different thread from `server()`, so the decrement belongs in its `finally`. Otherwise the count only goes up, and the server eventually rejects everyone.
- **A lock is needed.**  
`count += 1` is not one step: it reads, adds, and writes. Two threads doing it at the same moment can overwrite each other's update, so the count would drift. Wrapping the change in a lock makes it happen one thread at a time.
- **Check and increment in one lock hold.**  
Otherwise two threads could both pass the check at the same moment.  

- **`global` is needed** in functions that reassign `active_clients`, or Python treats it as a local variable.
- **Accept first, then check.**   
If the check came before `accept()`, a rejected client would sit in the OS backlog believing it was connected. By accepting first, the server can tell the client `Error : server is full` and close.
- **The backlog (`listen(5)`) is not a client limit.**   
It only limits connections waiting to be accepted, and my server accepts almost instantly.
- **Rejected clients are never counted**, so there is nothing to give back for them.

### Test

I set `max_clients = 4` and ran the idle-connection script with `COUNT = 10`.

**Result:**   
The first four connections were accepted and the remaining six were rejected.

After the idle timeout passed, I ran the script again and four connections were accepted again, so the counter did not leak: the slots were given back when idle clients timed out.

## Bugs I hit

- **`TypeError` from a stray comma.** I wrote:

```python
max_message_length = 1024,
```

The trailing comma makes the value a **tuple**, `(1024,)`, not the number 1024. As soon as the server compared a length with it, Python raised:

```
TypeError: '>' not supported between instances of 'int' and 'tuple'
```
The fix is to remove the comma:

```python
max_message_length = 1024
```
- The count of rejected clients was added before the check, so the count could leak and the limit was off by one (the check `active_clients < max_clients` after incrementing allowed only 3 clients with `max_clients = 4`).
- Missing `global active_clients` in functions that change the counter.
- A rejected client was never told and its socket was never closed.

**Lesson**   
A counter that goes up must have a matching place where it goes down, and a limit check has to happen before the increment, in the same lock hold.

## Limitations

- **The cap is shared by everyone.**   
One client opening four connections can fill every slot and lock everyone else out for as long as it keeps them busy. A real server would also limit connections **per IP address**.
- **The idle timeout only removes idle clients.**   
A client that sends a valid message every few seconds is never timed out.
- **Rate limiting is not implemented yet.**   
A client sending thousands of valid messages per second can still use CPU and bandwidth.

## Defense 3: Rate limiting

**The problem**  
The other limits don't catch a client that sends thousands of short, valid messages per second. Each message is well-formed, the connection is never idle, and it uses only one connection, so the server keeps working on them and uses CPU and bandwidth.   
Rate limiting caps how many messages one client may send in a given time.

**Method: Fixed window counter**  
Each client has two variables:

- `message_count`: Messages seen in the current window
- `window_start`: When the current window began

The window is not a background timer. It is one stored timestamp that is compared with the current time each time a message arrives.

```python
max_messages = 5     # messages allowed per window
rate_window = 1      # window length in seconds

def handle_client(client_socket, address):
    ...
    message_buffer = b""
    message_count = 0
    window_start = time.monotonic()

    ...
            while b"\n" in message_buffer:
                line, message_buffer = message_buffer.split(b"\n", 1)
                ...
                # Rate limiting: allow at most max_messages per rate_window seconds.
                # If the current window has run out, start a new one and reset the count.
                now = time.monotonic()

                if now - window_start >= rate_window:
                    window_start = now
                    message_count = 0

                message_count += 1

                if message_count > max_messages:
                    send_error(client_socket, "Error: rate limit exceeded")
                    return
```

**Design notes**
- **Per-client variables, no lock.**   
Each client's counter is used only by that client's thread, so it is an ordinary local variable. This differs from `active_clients`, which many threads share and so needs a lock.
- **Created before the loop.**   
If they were created inside the loop, they would reset on every pass and the count would never get above 1.
- **Both assignments in the `if` are needed.**  
The ones before the loop set the starting state once. The ones inside the `if` start a new window each time the old one runs out. Without the reset, the count only goes up, and even a slow, polite client would eventually be disconnected.
- **`time.monotonic()`** returns a value that only goes forward, so it is right for measuring durations. The normal clock can jump if the system time changes.
- **Compare elapsed time, not the timestamp.**   
`window_start` is a point in time, so the check must be `now - window_start`.
- **Count first, then compare.**  
Increasing the count and then checking `> max_messages` lets exactly 5 messages through and rejects the sixth.
- **Placed before the empty and printable checks**, so rejected messages still count toward the limit and a client can't flood the server with empty messages for free.
- **Counts messages, not `recv()` calls.** It sits inside the inner loop, once per complete message.

**Policy:**   
The server sends an error and disconnects the client. A client that breaks the rate rule is dropped, and its thread is freed.

### Test

| Test | Script sends | Result |
|---|---|---|
| Flood | `b"hi\n" * 20` in one `sendall()` | Five echoes, then `Error : Rate limit exceeded`, then the connection closed |
| Polite client | 5 messages, wait 1.2 s, 5 more messages | All ten echoed, so the window reset |

The polite client test shows that this is a limit on the rate and not on the total number of messages.

## Bugs found in code review

These were caught when reviewing the code before testing, and I did not trigger them as runtime errors:

- Compared `window_start` directly with `rate_window`.   
`window_start` is a point in time, so the check was almost always false and the client would be disconnected on its first message. The correct comparison is `now - window_start`.
- No reset of `window_start` and `message_count`, so the count would only go up.
- `return window_start` returned a number to nobody, with no error sent to the client.
- Off by one:   
Incrementing inside the `if` allowed 6 messages through.
- Deleted the two variables before the loop while editing, which would raise `UnboundLocalError` on the first message.
- Check 2 was indented inside the inner `while`, so it only ran when a newline was present and the unbounded buffer problem came back. It needs to sit after the loop, at the same indentation as `while b"\n" in message_buffer:`.

**Lesson:**   
After editing a block, re-run the earlier tests. A change in one place (the rate-limit block) can break something else (Check 2 moved).

## Limitations

- **A client can reconnect and start a new count.**   
Nothing remembers that it was rate limited. Tracking clients by IP address would fix this.
- **Fixed windows allow a burst at the boundary.**   
A client could send 5 messages at the end of one window and 5 more at the start of the next, so 10 arrive in a very short time. Sliding-window or token-bucket methods avoid this. I did not test this behavior.
- **The limits are low testing values:**   
`max_clients = 4`, `idle_timeout = 10`, `max_messages = 5`.
