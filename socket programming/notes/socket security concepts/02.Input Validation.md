# Input validation
This is the process of checking external data against a set of predefined rules before the server can process it.  
Unchecked input can crash a thread, confuse the server, or open the way to worse problems.   
 
**Checks for a chat server**
- Encoding: is the data valid UTF-8?
- Length: is the message too long?
- Content: is it empty or full of unexpected characters?
- Format: does it follow the format the server expects?

## Check 1: Encoding

**The problem**  
`recv()` returns bytes, and `decode('UTF-8')` turns them into text. If the bytes aren't valid UTF-8, `decode()` raises `UnicodeDecodeError`.

A helper function has been included in the code during the remaining checks;  

```python
def send_error(client_socket, text):
try:
client_socket.sendall((text + "\n").encode("UTF-8"))
except OSError:
pass
```

**Prediction vs. result**
My original chat server did not handle this error.  
`UnicodeDecodeError` is a subclass of `ValueError`, not `OSError`, so `except OSError` doesn't catch it.  
The exception escaped `handle_client`, the `finally` block closed that client's socket, and only that client's thread ended. The server is expected to keep running.

**Text vs. bytes (a lesson from testing)**  
Typing `\xff\xfe\xfd` into my client sent the *text* of those characters, which is valid UTF-8. The client turns typed input into a string, so it can't send raw invalid bytes.   

To send real bytes, I used a separate script that calls `sendall()` with a bytes literal (`b"\xff\xfe\xfd"`).

**Test script**
```python
import socket

s = socket.create_connection(("127.0.0.1", 8080))
s.settimeout(3)
s.sendall(b"\xff\xfe\xfd")

try:
    reply = s.recv(1024)
    print("Server replied:", reply.decode("UTF-8", errors="replace"))
except socket.timeout:
    print("No reply received.")

s.close()
```

**Bugs I hit while testing**

- A missing backslash in the test bytes.    
I wrote `b"xff\xfe\xfd"` instead of `b"\xff\xfe\xfd"`. The error message gave it away:  

```
UnicodeDecodeError: 'utf-8' codec can't decode byte 0xfe in position 3: invalid start byte
```

I expected the error to name byte `0xff` at position 0, since that was meant to be the first invalid byte. Instead it named `0xfe` at position 3. Without the backslash, `xff` was sent as three plain characters (`x`, `f`, `f`) in positions 0 to 2, which are valid UTF-8. The first invalid byte was therefore `0xfe`, in position 3.

**Lesson:**   
The byte value and position in a `UnicodeDecodeError` show exactly where decoding failed, so they can be compared with what was meant to be sent.

- The server code had been edited but not restarted, so the old code was still running.
- The test script closed the connection without reading, so it never received the server's reply.  

| | Bytes sent | First invalid byte |
|---|---|---|
| Intended | `\xff \xfe \xfd` | `0xff` at position 0 |
| Actual (typo) | `x f f \xfe \xfd` | `0xfe` at position 3 |

**The fix on the server**
```python
except UnicodeDecodeError:
    print(f"Non-UTF-8 data received from {address}.")
    try:
        client_socket.sendall(b"Error : invalid message encoding.\n")
    except OSError:
        pass
```  

The inner `try/except` handles the case where the client has already disconnected.

**Design decision**  
When a client sends invalid data, the server replies with an error message and then disconnects the client (the `finally` block closes the socket).   
Alternatives were to ignore the message or to keep the connection open. Disconnecting rejects a misbehaving client. Rate limiting may be added later to handle repeated bad input.

**Result**  
Server replied:   
Error : invalid message encoding.  

## Check 2: Message length

**The problem**  
A server that doesn't limit message size can be forced to use unbounded memory. The first step was to see how my server handled a message longer than one `recv()` call.
   
**Experiment: a 3000-byte message**  
I sent 3000 bytes in one `sendall()` to the original server (before framing and length checks were added), using this script:

```python
import socket

s = socket.create_connection(("127.0.0.1", 8080))
s.settimeout(3)
s.sendall(b"A" * 3000)

try:
    while True:
        reply = s.recv(1024)
        if not reply:
            break
        print(f"Reply chunk: {len(reply)} bytes")
except socket.timeout:
    pass

s.close()
```

Output on the client:

```
Reply chunk: 1024 bytes
Reply chunk: 1 bytes
Reply chunk: 1024 bytes
Reply chunk: 1 bytes
Reply chunk: 953 bytes
```

The chunks add up to 3003 bytes: the 3000 bytes sent plus a leading space added to each of three echoes. This is consistent with the server reading the message in three pieces, because `recv(1024)` returns at most 1024 bytes per call. The client's own `recv(1024)` then split the replies into five chunks.  

**What this shows: TCP is a byte stream**  
TCP doesn't preserve message boundaries. One message can arrive in several reads, and several messages can arrive in one read.   

`recv(1024)` is how much I read per call, not how long a message is. Without a rule for where a message ends, the server can't tell a long message from several short ones, and it can't enforce a maximum length.

### Message framing

**Rule:** Every message ends with a newline (`\n`).

**Server side:** Each client gets a buffer. New data is appended to it and complete messages extracted whenever a newline is present.

```python
message_buffer = b""

while True:
    data = client_socket.recv(1024)
    if not data:
        break

    message_buffer += data

    while b"\n" in message_buffer:
        line, message_buffer = message_buffer.split(b"\n", 1)
        # handle one complete message here
```

- `+=` adds new data after any leftover bytes, so an unfinished message waits for the rest.
- `split(b"\n", 1)` cuts at the first newline and returns the complete message and everything after it.
- The inner loop is a `while`, not an `if`, because one `recv()` can contain several complete messages.
- `recv()` returns bytes, so the buffer and the delimiter are bytes (`b""`, `b"\n"`).

**Client side:**   
`input()` removes the newline the user typed with Enter, so the client adds it before sending: `sendall((text + "\n").encode("UTF-8"))`.

**Side benefit:**   
Decoding only the complete lines means a multi-byte UTF-8 character can no longer be split across two chunks and cause a false `UnicodeDecodeError`.

### The length limit

`max_message_length` is the largest message accepted (bytes before the newline). It's separate from the `recv()` size.

**Two checks are needed:**

1. **Complete line too long.**  
After extracting a line, check `len(line)`. This catches a long message that does end with a newline.
2. **Leftover buffer too long.**   
After the inner loop, the buffer holds only an unfinished message. If it already exceeds the limit, no valid message can follow, so it's rejected. This catches long data that never contains a newline.

```python
if len(line) > max_message_length:
    send_error(client_socket, "Error : message too long.")
    return

# after the inner while loop:
if len(message_buffer) > max_message_length:
    send_error(client_socket, "Error : message too long.")
    return
```

`return` inside the `try` still runs the `finally` block, which closes the socket. That's the disconnect.

**Why disconnect instead of truncate or keep buffering?**

| Option | Problem |
|---|---|
| Keep buffering | A client can send data forever with no newline, exhausting memory (resource exhaustion). |
| Truncate at the limit | The remaining bytes become the start of the next message, breaking the message boundaries. |
| Send an error and disconnect | The server stays in a known state and uses bounded memory. |

Real servers do the same. For example, web servers answer oversized requests with an error status and close the connection.

**Memory bound:**   
With a 1024-byte limit and `recv(1024)`, a client's buffer can't grow much past about 2000 bytes before it's rejected.

### Testing

I temporarily set `max_message_length = 10` so that short inputs would trigger the checks. With my TCP client:

| Input | Result |
|---|---|
| hello | Echoed (below the limit) |
| this is way too long | Error, connection closed (Check 1) |

### Bugs I hit

- `message_buffer.split("\n", 1)` raised `TypeError : a bytes-like object is required, not 'str'` because the buffer is bytes and `"\n"` is a string. It needs `b"\n"`.
- An infinite loop printed the same message repeatedly. 
- **Infinite loop (buffer not reassigned).**   
I wrote:

```python
line, buffer = message_buffer.split(b"\n", 1)
```

The leftover bytes went into a new variable called `buffer`, but the loop condition checks `message_buffer`. Since `message_buffer` never changed, `b"\n" in message_buffer` stayed true forever, so the server kept handling the same message and printed it over and over. The fix is to assign the leftover back to the variable the loop checks:

  ```python
  line, message_buffer = message_buffer.split(b"\n", 1)
  ```

**Lesson:**   
A `while` loop must change something its condition depends on. When a loop never ends, check that the variable in the condition is actually being updated.
- A test script sent data without the final `\n`, so the server waited for the end of the message and never replied. This happened with several of my scripts.

**Lesson:**   
When testing a server, send exactly what you mean to send, including the newline.

## Check 3: Content (empty messages and control characters)

**The problem**  
A message can be valid UTF-8 and within the length limit and still be unwanted:

- **Empty messages:** An empty line, or one containing only spaces, has no content to relay.
- **Control characters:** Characters such as the bell (`\x07`), backspace, or carriage return (`\r`) aren't meant to be displayed. Printing them can mess up the terminal of whoever runs the server, and they can be used to forge or hide log lines (log injection).

**The checks**

```python
message = line.decode("UTF-8")

if not message.strip():
    send_error(client_socket, "Error : message is empty")
    continue

if not message.isprintable():
    send_error(client_socket, "Error : message contains invalid characters")
    continue

print(f"Received the following from the client {message}")
```

- `strip()` removes leading and trailing whitespace, so `""` and `"   "` are both caught by one check.
- `isprintable()` is true for letters, digits, punctuation, spaces, and emoji, and false for control characters.
- `continue` skips the rest of the loop body and moves on to the next message in the buffer.
- **Order matters.**  
Both checks come after `decode()` and **before** the `print()` and the echo, so a rejected message is never logged or sent back.

**Design decision: keep the connection open**

| Failure | Response | Connection |
|---|---|---|
| Invalid encoding | Error sent | Closed |
| Message too long | Error sent | Closed |
| Empty message | Error sent | Stays open |
| Control characters | Error sent | Stays open |

Invalid encoding  suggest a broken or hostile client and oversized data can use up server memory, so they get disconnected. An empty message is usually an accidental Enter press, so disconnecting would be too harsh. If a client sends a flood of empty or invalid messages, that is a rate-limiting problem, which comes later.

**Limitation:**   
`isprintable()` is also false for the tab character, so a message containing a tab is rejected. That is acceptable for this chat server.

### Testing

**Empty messages (TCP client):**   
Pressed Enter with nothing typed, then typed only spaces, then `hello`.

| Input | Result |
|---|---|
| (empty) | The data received from server is: Error : message is empty |
| spaces only | The data received from server is: Error : message is empty |
| `hello` | The data received from server is:  hello |

**Control characters (script):**

```python
import socket

s = socket.create_connection(("127.0.0.1", 8080))
s.settimeout(3)
s.sendall(b"hi\x07there\n")

try:
    print("Server replied:", s.recv(1024).decode("UTF-8", errors="replace"))
except socket.timeout:
    print("No reply.")
s.close()
```

Result:   
"Server replied: Error : message contains invalid characters"

**Typed text vs. real bytes**  
Typing `\x07` at the client's prompt sends four ordinary characters (a backslash, `x`, `0`, `7`), which are printable and pass the check. Only a script that sends real bytes (`b"\x07"`) tests it, which is the same lesson as the invalid UTF-8 test.

### Debugging notes

My first test script got "No reply" from the server. Adding a temporary `print(repr(data))` to the server code showed what the server actually received:

```
b'hi\x07there'
b''
```

- The first line shows the bell byte did arrive as a real `\x07`.
- There was **no `\n` at the end**, so the server kept waiting for the end of the message and never ran any check.
- The second line, `b''`, is `recv()` reporting that the script had disconnected after its 3-second timeout.

The fix was adding `\n` to the end of the bytes sent by the script.

**Tools learned:**
- `repr()` shows the exact characters in a string, including invisible ones, so it can tell `\x07` (a real control character) apart from `\\x07` (typed text).
- The newline is part of the protocol: a message that doesn't end with `\n` is never processed.

## What I learned
Input validation is very important to any server program in order to ensure security.   
Control characters such as \r can hide or alter what appears in the server’s terminal or logs, so rejecting them stops attackers from making log output misleading.
