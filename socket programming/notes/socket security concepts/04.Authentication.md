# Authentication

**The idea**  
Three terms that are easy to mix up:

| Term | Question it answers | Example |
|---|---|---|
| Authentication | Who are you? | Username and password at login |
| Authorization | What are you allowed to do? | Only admins can remove users |
| Encryption | Who can read the traffic? | TLS |

My server used to accept anyone who connected. Now a client must log in before it can chat.   
Authorization is not implemented. Encryption comes with TLS.

**Where login happens**  
The login cannot happen before `accept()`, because the server needs a live connection to receive credentials on. It happens at the start of `handle_client`, before the chat loop.   
An unauthenticated client still holds a thread and a client slot, so the existing limits cover it:

- The idle timeout stops a client that connects and never logs in.
- `max_clients` counts it
- The failed-attempt limit stops password guessing

**Never rely on the client to enforce a rule.**   
Anyone can write their own client or use a tool like `nc`, so only the server's check counts.

## The login flow

```
Server: Username:
Client: Bob
Server: Password:
Client: pass123
Server: Successful login        (or: Error: invalid login details)
```

- Up to 3 attempts (`max_login_attempts = 3`). Each attempt counts, whether it fails or not.
- Every failed attempt gets the same generic message, so an attacker can't tell whether the username or the password was wrong.
- After three failures the server sends `Error: too many failed attempts` and disconnects.
- If the client disconnects during login, the server stops quietly. The connection is gone, so there is nobody to notify. The `finally` block closes the socket and releases the client slot.

**Why 3?**   
There is no universal rule. It is a convention that balances honest typos against guessing attacks. Locking an account after failures has a cost; an attacker could lock out a real user on purpose.

## Code

```python
max_login_attempts = 3
users = {"Bob": "pass123"}   # demo credentials only, hashing comes later
```

`read_line` reads one complete line, using the same buffer as the chat loop:

```python
def read_line(client_socket, message_buffer):
    while True:
        if b"\n" in message_buffer:
            line, message_buffer = message_buffer.split(b"\n", 1)
            if len(line) > max_message_length:
                send_error(client_socket, "Error: message too long")
                return None, message_buffer
            return line, message_buffer

        if len(message_buffer) > max_message_length:
            send_error(client_socket, "Error: message too long")
            return None, message_buffer

        info = client_socket.recv(1024)
        if not info:
            return None, message_buffer
        message_buffer += info
```

`authenticate` returns `(success, message_buffer)`:

```python
def authenticate(client_socket, message_buffer):
    for attempt in range(max_login_attempts):
        send_line(client_socket, "Username:")
        line, message_buffer = read_line(client_socket, message_buffer)
        if line is None:
            return False, message_buffer
        username = line.decode("UTF-8").strip()

        send_line(client_socket, "Password:")
        line, message_buffer = read_line(client_socket, message_buffer)
        if line is None:
            return False, message_buffer
        password = line.decode("UTF-8").strip()

        if users.get(username) == password:
            send_line(client_socket, "Login successful")
            return True, message_buffer

        send_line(client_socket, "Error: invalid username or password")

    send_line(client_socket, "Error: too many failed attempts")
    return False, message_buffer
```

In `handle_client`, inside the `try` and before the chat loop:

```python
success, message_buffer = authenticate(client_socket, message_buffer)
if not success:
    return
```

**Design notes**
- `read_line` returns `(None, buffer)` for both a disconnect and an oversized line, so the caller handles one case: stop.
- It returns the buffer too, so bytes the client sent after the password line are not lost.
- It checks the buffer for a newline before calling `recv()`, because a client can send several lines at once.
- `users.get(username)` returns `None` for an unknown user, and `None` never equals a password string. One comparison covers both failures with the same message.
- The login runs inside the `try`, so the existing `except socket.timeout` and `except OSError` handlers cover it.

## Test

Tested with `nc 127.0.0.1 8080`, which needs no client code:

| Input | Result |
|---|---|
| `Bob`, `pass123` | Successful login, then chat echoes |
| Wrong password | Invalid login details |
| Three wrong attempts | Too many failed attempts |

The password is visible on screen as it is typed, because `nc` is a raw connection. A real client should hide it.

## Bugs I hit

- **Return value ignored.**   
I called `authenticate(client_socket, message_buffer)` without using what it returned. The chat loop started even for a failed login, and my username and password were echoed back with a leading space, because the chat loop was reading them. The fix is `success, message_buffer = authenticate(...)` followed by `if not success: return`.
- **Wrong disconnect test in `read_line`.**   
I had `if not message_buffer.strip(): return None, ...`. An empty buffer means no data has arrived *yet*, not that the client left, so the function returned before calling `recv()`. The server sent `Username:` and disconnected, and I never saw `Password:`. The only sign of a disconnect is `recv()` returning `b""`.

These were found in code review before I could run them:

- `for attempt in max_login_attempts` needs `range(...)`.
- `recv()` was called directly during login, and the result of `read_line` was ignored.
- The dictionary was a single record, and `users.get("name")` shape should be username to password.
- A string was returned where `True` or `False` was needed.


**Lesson:**   
A function that signals success or failure is useless unless the caller uses the result.

## Limitations

- **Passwords travel in plain text.**  
I captured a login on the `lo` interface with Wireshark (filter `tcp.port == 8080`).   
*Follow → TCP Stream* showed the username prompt, `Bob`, the password prompt, `pass123`, `Login successful`, and my chat messages as readable text.  
Authentication alone does not protect the credentials, because they cross the network unencrypted. This is the reason for adding TLS.
- **Passwords are stored in plain text** in a dictionary.   
Hashing comes with the File Handling and Hashing topic.
- **A client can reconnect and get 3 more attempts.**   
Tracking failed logins per IP address would fix this.
- **No authorization.**   
Every logged-in user can do the same thing.
- **No password hiding with `nc`.**   
The secure client will use `getpass`.
